Green Egg: the Flying Blind V3 test bed

I chose the Estes Green Egg rocket as the test bed for Flying Blind V3 because its payload compartment provided an affordable way to carry and test the flight computer.

I started by connecting sensors on a solderless breadboard. I moved to a smaller Teensy processor and soldered wiring for V2, then consolidated the assembly onto a PCB for V3. All three retained the same IMU, barometer, and microSD storage. My recent software work uses V2 to develop recording, analysis, calibration checks, and altitude estimation before porting the proven software to V3.

Learning to solder with low vision

Soldering was difficult because my vision makes small components and joints hard to see. My dad taught me the technique, and better soldering equipment, magnification, and practice helped me improve.

Flying Blind V2 / Software progression

From readings on a screen to inspectable data

I developed the software in small, tested steps: blink and USB serial, sensor communication, combined readings, scheduled acquisition, microSD readback, and separate recording sessions. Each milestone has its own Git commit and test notes, so the results can be traced back to the code and data.

Acquire and record

Pressure, barometer temperature, three acceleration axes, and three gyro axes are read together as a sample group. The readings are acquired sequentially, with a sample number and an elapsed acquisition-start timestamp.

Bench tests verified 60-row sessions with 1,000 ms between recorded acquisition starts. Each startup uses a new filename, and saved files were checked on the computer. The current bench capture stops saving after 60 successful rows; live readings continue.

Analyze and compare

Python scripts check column layouts, numeric fields, sample continuity, and timestamp spacing. They calculate averages, sample standard deviations, ranges, and acceleration magnitude, then plot each recording without removing samples.

The tools support the original sensor logs, raw-plus-corrected gyro logs, and the new Kalman-output format. Original recordings are preserved separately from derived results.

Check calibration

A fixed gyro-offset profile estimated from one warmed-up stationary recording was tested on a separate recording, then implemented in firmware. Both raw and corrected gyro readings are saved.

Manual checks confirmed the accelerometer axis signs and both gyro rotation directions. Full accelerometer calibration, temperature testing, and dynamic accuracy validation remain in progress.

Measured evidence / Stationary bench tests

Keeping the raw values makes improvements visible

In SEN002, the saved file contained 60 consecutive samples and 59 acquisition intervals of exactly 1,000 ms. Pressure averaged 1005.116 mbar with a sample standard deviation of 0.114 mbar. These numbers describe this short bench recording; they do not establish absolute pressure accuracy or high-frequency noise performance.

An independent check before using the correction

I estimated gyro offsets from SEN004, then held that profile fixed and applied it to SEN006. Assuming the board remained stationary, the change in mean readings supports transferring the offset correction to a new recording. It is a stationary bias check, not a calibration of angular-rate accuracy.

Software progression / Altitude estimation

An experimental altitude Kalman filter

The latest V2 firmware adds a two-state Kalman filter that estimates relative altitude and vertical velocity from barometric measurements. The first accepted pressure reading defines relative zero. The filter predicts motion using a constant-velocity model, then corrects its estimate with the next barometric altitude measurement.

This version uses the barometer only. IMU acceleration is still recorded, but is not fused into altitude estimation. Accelerometer calibration, orientation processing, and gravity removal are prerequisites for that next stage.

The Teensy 4.0 build passed. Desktop numerical tests compared the filter with an independent matrix implementation over 3,000 variable-interval updates and checked invalid inputs, covariance behavior, and a synthetic stationary case. These checks establish numerical consistency. The next evaluation compares altitude estimates with measured height changes.

New KAL sessions retain the raw measurements and append barometric altitude, filtered altitude, estimated vertical velocity, model uncertainty, reference pressure, and provisional tuning settings. The filter is experimental, with provisional tuning. Its uncertainty values describe the model assumptions; evaluation against measured heights is the next step.

A debugging example

When a sensor stopped responding

When the MPU6050 disappeared from the I²C scan, I restored earlier working code to check whether the software changes explained the failure. The sensor was still absent. Supply-voltage and continuity checks then helped locate an intermittent SCL connection. Resoldering the joint restored both sensor addresses and live readings.

Later initialization failures and barometer read errors were also recorded. The repair is evidence about that incident, not proof that every reliability issue is solved. Component diagnostics and repeated startup testing remain unfinished.

Flight test / What happened

Testing V3 in the Green Egg

I flew the Green Egg rocket carrying Flying Blind V3, bringing the circuit board, printed sled, battery, and rocket together in a flight test.

That experience shaped the next preflight checklist: reset the software after power-on, confirm that recording has started, and check the saved session after the test.
